# GRF Workbench

Плагин bb для работы с ресурсами Ragnarok из GRF и визуальной проверки результата. Референс реализации — **текущий игровой клиент midgard-ro**. Вкладки: **Skill Studio**, **Ресурсы GRF**, **Снимки и замечания**.

## Skill Studio — этап 1

Откройте **Skill Studio** в панели обсуждения. Автономная сцена запускает Soul Strike между Mage и Rocker, используя существующий процедурный генератор, рендер персонажей, камеру и финальный проход эффектов клиента. Сервер не нужен. Сейчас воспроизводятся полёт, хвосты и вспышки; акторы находятся в idle. Каст, звук, реакция цели, другие навыки и семантическая библиотека — следующие этапы [плана](../../docs/plans/skill-studio.md).

- Play/Pause, шаг 1/60 секунды, таймлайн, скорость просмотра; уровень задаёт число попаданий из клиентской таблицы, тестовый вход может его переопределить. Число снарядов показывается отдельно.
- Вращение средней кнопкой или левой в режиме «Вращать», ракурсы ±45°, колесо — zoom; Space + левая или Shift + средняя — pan. Центр: Mage, Rocker или середина действия. Наклон пока игровой, фиксированный.
- **Обновить параметры** перечитывает общее [определение Soul Strike](../../internal/engine/skillvisual/definitions/effects/soul_strike.yaml) без компиляции. Размер, подъём и разброс применяются также клиентом из той же рабочей копии при следующем запуске эффекта. Остальные характеристики пока заданы существующим Go-кодом.
- **Пересобрать / загрузить ресурсы** перезапускает worker и проверяет хеш исходников; после изменения Go-кода собирается новая версия. Новый процесс открывается с выбранным временем и камерой. Изменение архивов требует этой кнопки.
- **Снимок и замечание** сохраняет lossless PNG именно показанного кадра и его `skillFrame`: время, сцену, anchors, параметры, зависимости с хешами и версию сборки. Обычные R/G/Delete и комментарии работают в просмотре снимка. Агент получает контекст через `grf_review_read`.
- **Вернуться к живой сцене** использует сохранённые параметры сцены с текущим кодом/данными. Это новый просмотр; старый снимок и ревизия сохраняются, автоматического восстановления старой сборки пока нет.

В версии 0.3.1 исправлен показ при непрерывном вращении/зуме: завершённые кадры больше не отбрасываются из-за нового положения камеры. Запросы объединяются до последнего состояния, одновременно выполняется один; следующий начинается без прежней паузы 40 мс. Планировщик допускает до 60 кадров/с в пределах скорости рендера и передачи. На неподвижной сцене остаётся только редкий запрос для сохранения сессии. Кнопки вращения и перемещения имеют пиктограммы; подписи различают живую сцену и сохранённый снимок с замечаниями.

Агентский инструмент `grf_studio_render` принимает сцену (tick, level, hits, separation, camera), возвращает PNG и контекст и сохраняет снимок для review. Он появляется в новых агентских сессиях после обновления плагина.

Для Studio дополнительно нужны SDL2, OpenGL 4.1 и доступ к графической сессии на **машине проекта**. На macOS используются системный OpenGL и установленный SDL2; на Linux требуется рабочий GL/display, включая виртуальный display для автоматической проверки. Worker создаёт скрытое окно; bb получает готовые кадры. Ограничение — четыре открытые сцены, один запрос кадра на сцену, закрытие процесса при выходе из вкладки и после двух минут без запросов. Живые кадры хранятся ограниченно в памяти; на диск попадают только сохранённые снимки и кэш бинарников. Первый холодный build может занять до двух минут.

Сборка отдельного worker и JSON-lines запрос для диагностики из корня проекта:

```sh
go build -o /tmp/midgard-skillstudio ./cmd/skillstudio
printf '%s\n' '{"tick":25,"level":10,"hits":0,"separation":12,"camera":{"yaw":0,"distance":190,"panX":0,"panZ":0,"focus":"center"}}' | /tmp/midgard-skillstudio
```

## Установка вместе с проектом

Плагин и его Go-движок версионируются в `avatar29A/midgard-ro`. Каталог `.bb/plugins.json` позволяет устанавливать Workbench по имени. Для разработки рекомендуется локальная установка из той же копии проекта, в которой работает агент:

```sh
# Из корня клонированного midgard-ro, содержащего Workbench:
npm ci --prefix plugins/bb-plugin-grf-workbench --include=dev
bb plugin install path:. --plugin grf-workbench
```

Нужны Node.js 22.19+ (22 LTS), Go из `go.mod` и bb 0.41+; CI проверяет bb 0.41.0 / Plugin SDK 0.4.34 на Linux и macOS. Плагин использует `config.yaml` и локальные архивы **окружения обсуждения**. Для GRF-функций это должна быть копия midgard-ro с `cmd/grfworkbench` и `internal/assetworkbench` из совместимой версии проекта.

После попадания кода в `main` доступна управляемая Git-установка:

```sh
bb plugin install git:https://github.com/avatar29A/midgard-ro.git@main --plugin grf-workbench
bb plugin outdated
bb plugin update grf-workbench
```

Git-установка обновляет пакет плагина, но не рабочую копию игрового клиента. При обновлении согласовывайте версию плагина и checkout проекта. Для воспроизводимой установки используйте один релизный тег для обоих; например, **после публикации** `grf-workbench/v0.2.3`:

```sh
git checkout grf-workbench/v0.2.3
bb plugin install git:https://github.com/avatar29A/midgard-ro.git@grf-workbench/v0.2.3 --plugin grf-workbench
```

Установка диапазона `@^0.2.3 --tag-prefix grf-workbench/ --plugin grf-workbench` получает совместимые patch-релизы через `bb plugin update`. Точный тег остаётся закреплённым. Локальная установка продолжает использовать исходную папку; для её разработки доступны `bb plugin dev plugins/bb-plugin-grf-workbench` или сборка/reload из раздела ниже. npm-публикация отключена (`private: true`); Git-установке это не мешает.

## Выпуск версии

1. Изменяйте UI/контракты и Go-часть одним PR, сохраняя совместимость и добавляя нужные тесты.
2. Обновите версию `package.json` и `package-lock.json`. Сохраните ID `grf-workbench` и append-only миграции базы, чтобы обновление сохраняло данные.
3. Дождитесь всех проверок CI, включая GRF Workbench на Linux/macOS: типы, тесты, общий Go-движок и сборку чистого пакета с `--omit=dev --omit=optional`.
4. После merge создайте тег на проверенном коммите `main` и отправьте его, например:

```sh
git tag -a grf-workbench/v0.2.3 -m 'GRF Workbench 0.2.3'
git push origin grf-workbench/v0.2.3
```

CI проверяет совпадение тега с версией пакета. Выпущенные теги не перемещать: исправление получает новую версию. Создание PR само по себе не публикует релизный тег.

В Git хранятся исходники, manifest, lockfile, документация и тестовые фикстуры. `node_modules` и `dist` исключены из коммитов; Git-установка собирает артефакты. Пользовательские GRF, снимки, комментарии и кэш живут отдельно: установка кода на другую машину не переносит их автоматически. Для отдельных проверок используйте экспорт `bb grf-review export`.

## Архивы, спрайты и анимации

1. Откройте GRF Workbench из панели обсуждения проекта. Архивы берутся из `config.yaml → data.grf_paths` на машине его окружения.
2. Ищите по имени или части пути, включая корейские имена. Фильтр поддерживает ACT, SPR, BMP, TGA, PNG, JPG и общий список файлов. Результаты разбиты на страницы по 50.
3. По умолчанию последний архив из конфигурации перекрывает предыдущие, как в клиенте. В списке видны источник и количество версий; можно выбрать отдельный архив. В таком режиме парный SPR/ACT тоже ищется в выбранном архиве; для совмещения patch ACT с базовым SPR используйте общий режим.
4. SPR показывает исходные изображения; кнопка парного ACT открывает анимацию. Для ACT доступны действия с направлениями, начальный кадр, воспроизведение, пауза, ползунок кадров и скорость. Кадры выбранной последовательности заранее собраны на общем холсте, без повторного чтения архива на каждом шаге.
   В превью любых ресурсов колёсико меняет масштаб, **Пробел + левая кнопка** или **средняя кнопка** перемещает изображение. Пробел в полях поиска и комментариях вводится обычным образом.
5. Нажмите **Выделить область и оставить замечание**. Workbench остановит воспроизведение и сохранит показанный кадр для аннотации. Вместе с PNG сохраняются путь внутри GRF, архивы зависимостей, их SHA-256, action/frame, origin, интервал и версия кода рендера.

Проверено на настоящих `data.grf` и `rdata.grf`: 174 959 уникальных нормализованных путей. Например, `data/sprite/npc/rocker.act` имеет 40 action-записей; action 0 содержит 22 кадра по 75 мс. Это исходные записи ACT, не 40 отдельных игровых действий.

Поддержка рендера в этой версии:

- BMP/TGA/PNG/JPEG: `formats.DecodeImage` и `texture.ImageToRGBA`, с переключаемой прозрачностью magenta.
  Декодеры BMP/JPEG/PNG регистрируются самим пакетом `formats`; отдельный GRF-инструмент не зависит от побочных импортов игрового приложения. Это проверяется запуском собранного исполняемого файла на BMP/JPEG внутри тестового GRF.
- SPR: `formats.ParseSPR`, включая indexed/RGBA-изображения.
- ACT: парный SPR и игровой `sprite.CompositeSprites`; тайминг через `charsprite.ActIntervalTickMs`. Последовательность использует общий origin/canvas. Это просмотр отдельной пары SPR/ACT, не конструктор полного персонажа с головой и экипировкой.
- ACT со свойствами, для которых нужен специализированный рендер эффектов, показывает предупреждение. Workbench не подменяет его универсальным собственным рендерером.
- RSM/RSW/GND/GAT/STR и другие типы доступны в поиске; их специализированный просмотр, 3D-сцены и диагностика глубины остаются следующими этапами.

Один preview ограничен 256 кадрами и 8 мегапикселями атласа. Для большого ресурса отключите последовательность и выберите конкретный кадр либо задайте более поздний начальный кадр. SPR без ACT можно перелистывать/воспроизводить как лист изображений; это не игровая ACT-анимация.

## Снимки и замечания

1. Выберите вкладку **Снимки и замечания**. Кнопка **Развернуть** открывает просторный просмотр.
2. Нажмите **Выбрать файл…**: откроется системный диалог PNG/JPEG, и выбранный снимок загрузится автоматически. Файл выбирается на устройстве, где открыт интерфейс bb, в том числе вне каталога проекта. Для файла на машине проекта используйте **Указать путь**, например `data/Screenshots/latest.png`. В этой форме можно также задать название и контекст сцены перед выбором файла. Поддерживаются PNG/JPEG до 32 MiB и 16 мегапикселей.
3. В режиме **Выделить область** обведите NPC/персонажа и участок стены. Колёсико мыши приближает и отдаляет изображение к точке под курсором (5–800%). Средняя кнопка мыши или **Пробел + левая кнопка** временно перемещает изображение; выделение и комментарий сохраняются. Можно также выбрать режим **Перемещать** для перетаскивания левой кнопкой. Выделение работает в любом направлении; Escape его отменяет.
4. Напишите, что наблюдается и что должно быть видно. Нажмите **Сохранить замечание**, затем **В обсуждение**. Последняя кнопка добавляет упоминание в черновик; сообщение отправляет пользователь.
5. Агент читает замечание через `grf_review_read`. После исправления откройте новый снимок и подтвердите результат кнопкой **Проверено** на исходном замечании. Старые записи и снимки сохраняются.

Нажмите на рамку или её номер, чтобы выбрать сохранённую область. Выбор выделяется ярким контуром, крупным номером и затемнением остального изображения; соответствующая карточка тоже подсвечивается. В карточке можно изменить комментарий и сохранить его либо нажать **Проверено** — комментарий и статус сохранятся вместе.

**R** включает изменение размера выбранной области: тяните маркеры на углах или сторонах, курсор показывает направление. **G** включает перемещение рамки целиком с сохранением размера. Клавиша G выбрана по аналогии с [Move/Grab в Blender](https://docs.blender.org/manual/en/4.4/scene_layout/object/editing/transform/move.html); R остаётся нашей клавишей изменения размера.

Рабочий сценарий: **R → изменить размер → G → поправить центрирование → Enter**. Переходы между R и G сохраняют общий черновик, Enter или повтор текущей клавиши применяет правку, Escape отменяет её целиком. Кнопки режимов и применения доступны над картинкой. Это работает и для нового несохранённого выделения. В полях ввода R/G остаются обычными буквами; Пробел + перетаскивание по-прежнему двигает изображение.

Границы ограничены исходным изображением, минимальный размер — 1 × 1 пиксель. Для сохранённой области новые координаты и заново вырезанный фрагмент записываются вместе с проверкой revision; комментарий сохраняется. Изменение границ сбрасывает отметку «Проверено». До применения исходная запись не меняется.

Красная корзина удаляет область вместе с её комментарием из текущего списка. **Delete / Backspace** удаляет выбранную область, когда фокус находится в панели, но не в поле ввода. Эти клавиши также отменяют новое несохранённое выделение. Последнее удаление можно отменить кнопкой **Вернуть**, пока панель открыта. Исходная картинка и другие области сохраняются; удалённые записи не показываются в поиске упоминаний и списках агента. Изменения проверяют revision, чтобы действие из старой вкладки не перезаписало более новое.

В сообщении агента можно открыть нужную панель карточкой:

```text
::grf-resource{id="RESOURCE_SHA256_ID"}
::grf-review{capture="CAPTURE_UUID"}
::grf-review{annotation="ANNOTATION_UUID"}
```

Не отмечайте область из текущего снимка как доказательство дефекта автоматически: пользователь должен указать проблемное место и ожидаемое поведение. Снимок сам по себе не определяет виновную модель, depth buffer или draw call.

## Команды для агентов

Команды выполняются из обсуждения bb и определяют машину через его environment:

```sh
bb grf-review assets search rocker act --json
bb grf-review assets inspect RESOURCE_ID --json
bb grf-review assets render RESOURCE_ID 0 0 --json
bb grf-review open data/Screenshots/latest.png --title 'Перекрытие стеной' --context 'Карта и координаты, если известны' --json
bb grf-review list --json
bb grf-review show CAPTURE_OR_ANNOTATION_UUID --json
bb grf-review export ANNOTATION_UUID data/Screenshots --json
```

`list` показывает до 20 последних снимков и до 20 последних замечаний каждого (комментарии сокращены до 200 символов). `show` для снимка возвращает до 20 последних замечаний; `show` для annotation ID — полную запись. Экспорт создаёт новый уникальный подкаталог в существующей папке рабочего окружения и возвращает пути к `original.png`/`original.jpg`, `region.png`, `review.json`. Откройте **оба изображения** перед диагностикой. CLI никогда не печатает base64 в текстовый вывод.

Native tools: `grf_search`, `grf_inspect`, `grf_render`, `grf_review_list`, `grf_review_read`. `grf_render` возвращает image content и метаданные; `animated=true` возвращает атлас кадров. CLI `assets render` возвращает метаданные одного кадра и preview ID. Новые tools доступны при следующем запуске/возобновлении сессии provider; для уже открытой сессии используйте CLI export и её инструмент просмотра изображений.

## Контракт изображения

- Выбор через диалог передаёт байты файла на машину проекта частями с проверкой SHA-256. Браузер не раскрывает абсолютный путь выбранного файла, поэтому в источнике сохраняется его имя. Отмена диалога ничего не меняет. Временные части удаляются после импорта/ошибки либо при завершении host worker.
- Импорт сохраняет копию файла с SHA-256 на машине исходного проекта. Перезапись `latest.png` не меняет импортированный кадр.
- Координаты `x/y/width/height` измеряются в пикселях исходного изображения, начало — слева сверху. Масштаб UI, прокрутка и HiDPI не меняют сохранённые координаты.
- Рамка рисуется поверх изображения. Crop создаётся на host из оригинала, а не из масштабированного screenshot интерфейса.
- Просмотр и export используют полное разрешение. PNG-кроп из JPEG содержит декодированные пиксели исходного JPEG без повторного JPEG-сжатия.
- Изображения для модели ограничены 2 MiB каждое. Если нужен меньший вариант, ответ указывает реальные размеры переданного изображения и оригинала. Точные пиксели всегда доступны через export.
- Статус замечания меняется с проверкой revision; старый ответ другой вкладки не перезапишет новый. Изменение статуса не переносит подтверждение на новый снимок.
- Аннотации и метаданные сохраняются в plugin database bb, изображения — в persistent dataDir host worker. Их жизненный цикл не зависит от React-панели.
- Native tool не меняет человеческие отметки проверки. Упоминание содержит ID и инструкции получения изображений; сам текст упоминания не заменяет image content.

## Разработка

```sh
npm ci --include=dev
npm run typecheck
npm test
bb plugin types --check
bb plugin build
bb plugin install . --yes
# После изменений уже установленного плагина:
bb plugin build
bb plugin reload grf-workbench
```

Зафиксированы bb 0.41 / SDK 0.4.34. Для GRF на машине проекта нужен Go из `go.mod`. Host entry собирает `cmd/grfworkbench` и кэширует бинарник по хешу исходников и зависимостей; SDL/OpenGL-контекст не требуется. Go-код остаётся в этом репозитории и использует те же пакеты, что игра. Для работы только со снимками Go не нужен. Backend не читает workspace через собственный `node:fs`: всё чтение/экспорт идёт на явный hostId через типизированный host entry. Пути, введённые вручную, ограничены рабочим каталогом, включая проверку symlink. Системный выбор файла передаёт только явно выбранные пользователем байты, не открывая серверу произвольный локальный путь. GRF-файлы не изменяются.

Тесты используют официальный BB SDK harness с настоящей SQLite: координаты, последовательность пользовательских действий, исходные пиксели crop, смена исходного файла, reload, remote host routing, stale revision, path confinement, chunked transport и публичные импорты SDK. Проверка схем и сборки не заменяет ручную оценку оформления панели.

GRF reader переведён на `ReadAt`, с проверкой границ таблицы и записей, ошибок zlib/чтения, флагов шифрования и лимитов декомпрессии. Go-тесты покрывают повреждённые таблицы, конкурентное чтение, приоритет архивов/корейские имена и сравнение каждого пикселя ACT-атласа с игровым композитором. SDK-тесты проверяют воспроизведение из предзагруженного атласа и происхождение кадра после перехода к аннотации.

Go-проверки из корня проекта:

```sh
go test ./pkg/grf ./pkg/formats ./internal/assetworkbench ./internal/engine/sprite ./internal/engine/charsprite
go test -race ./pkg/grf
```
